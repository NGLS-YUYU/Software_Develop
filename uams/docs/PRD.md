## 1. 项目概述

高校教务教学管理系统（UAMS）是一套面向高校日常教学管理场景设计的多角色 Web 应用。系统以「学生、教师、教务管理员」三类核心用户为中心，通过统一身份认证、RBAC 权限控制和统一数据模型，形成课程、培养方案、开课、排课、选课、课表、考试、成绩、教学评价与通知等业务闭环。

项目定位不是简单的信息增删改查 Demo，而是以高校真实教学业务为背景，围绕「课程如何开出来、学生如何选、教师如何教、成绩如何产生、考试如何安排、教务如何管理」建立可运行的业务系统。

## 2. 项目背景与问题定义

### 2.1 业务背景

高校教学管理涉及大量基础数据与过程数据，包括学院、专业、班级、学生、教师、课程、教学班、教室、时间、选课、考试、成绩等。系统需要在角色隔离的同时保持这些数据之间的关联。

### 2.2 主要问题

- 教学基础数据分散，维护成本高；
- 人工排课、选课容易出现时间和资源冲突；
- 学生查看课表、成绩、考试安排不够集中；
- 教师成绩录入、提交和审核缺乏清晰流程；
- 教务人员需要重复统计课程、学生、成绩等数据；
- 多角色系统如果仅依赖前端菜单控制，容易产生越权访问风险。

### 2.3 设计原则

- 业务闭环优先：先保证核心教学链路可运行；
- 权限最小化：不同角色只能访问其职责范围内的数据；
- 数据一致性优先：选课、成绩等关键业务保证事务完整性；
- 技术稳定优先：减少不必要的数据库特性和复杂依赖；
- 可扩展：为毕业审核、学籍、智能排课等后续能力预留空间。

## 4. 用户角色与权限体系

### 4.1 角色

| 角色 | 角色代码 | 主要职责 |
|---|---|---|
| 学生 | STUDENT | 查看教学信息、选课、查看课表、成绩和考试等 |
| 教师 | TEACHER | 查看授课任务、学生名单、课表、录入并提交成绩等 |
| 教务管理员 | ACADEMIC_ADMIN | 维护教学基础数据、开课、排课、考试、成绩审核等 |

### 4.2 权限模型

采用 RBAC（Role-Based Access Control）模型：`User → Role → Permission`。前端负责菜单展示和路由控制，后端 API 必须执行最终权限校验。

```
User → Role → Permission → Page / API / Business Action
```

### 4.3 数据权限

- 学生：只能访问本人数据；
- 教师：只能访问本人授课课程及其教学班学生；
- 教务管理员：可以管理全校教学业务数据；
- 所有关键资源均需后端进行对象级权限校验，不能只依赖角色级菜单控制。

## 5. 系统总体架构

### 5.1 技术架构

```
Vue 3 + TypeScript + Vite + Element Plus
        ↓
      Axios
        ↓
    FastAPI
        ↓
  Service Layer
        ↓
SQLAlchemy 2.x / Repository
        ↓
  PyMySQL 驱动
        ↓
MySQL 8.4（InnoDB / utf8mb4）
```

### 5.2 组件职责

| 组件 | 技术 | 职责 |
|---|---|---|
| 前端 | Vue 3 / TypeScript / Vite | 页面、交互、路由、状态管理、权限菜单 |
| UI | Element Plus | 表格、表单、弹窗、分页、通知等后台业务组件 |
| 后端 | FastAPI | REST API、认证、权限、业务服务 |
| ORM | SQLAlchemy 2.x | 数据模型、查询、事务管理 |
| 数据库驱动 | PyMySQL | 通过 MySQL 协议连接 MySQL 8.4 |
| 数据库 | MySQL 8.4 | 持久化核心业务数据 |
| 迁移 | Alembic | 数据库结构版本管理 |
| 测试 | Pytest | 单元测试与 API/集成测试 |
| 版本控制 | Git / GitHub | 代码和文档版本管理 |

### 5.3 MySQL 使用原则

- 数据库使用 MySQL 8.4 LTS，不使用 SQLite 作为替代方案；
- 存储引擎使用 InnoDB，字符集必须使用 utf8mb4；
- SQLAlchemy 层优先使用通用 SQL 能力；
- 谨慎使用 JSON 类型、生成列、存储过程、触发器等非必要特性；
- 任何特殊 SQL、数据库函数或并发控制方案在实现前必须验证 MySQL 兼容性；
- 数据库结构统一由 Alembic 管理。

## 7. 核心业务流程

### 7.1 课程开设流程

```
课程 → 培养方案 → 开课任务 → 教学班 → 分配教师 → 安排教室与时间 → 开放选课
```

### 7.2 学生选课流程

```
学生登录 → 查询可选课程 → 提交选课
→ 后端校验：时间 / 容量 / 重复 / 先修 / 资格
→ 事务提交 → 生成选课记录 → 课表自动形成
```

### 7.3 成绩流程

```
教师进入教学班 → 录入成绩 → 保存草稿 → 提交成绩
→ 教务审核
    ├─ 驳回 → 教师修改后重新提交
    └─ 通过 → 正式发布
→ 学生查询成绩
```

### 7.4 考试流程

```
教务创建考试 → 指定课程 → 设置时间/地点/考场 → 发布 → 学生查询考试安排
```

## 11. 统一认证与权限需求

### 11.1 登录

支持用户名/学号/工号 + 密码登录。登录成功后由后端返回认证信息和角色信息，前端根据角色跳转对应首页。

### 11.2 路由

| 角色 | 默认首页 |
|---|---|
| 学生 | `/student/dashboard` |
| 教师 | `/teacher/dashboard` |
| 教务管理员 | `/admin/dashboard` |

### 11.3 安全要求

- 密码必须以安全哈希形式保存（bcrypt）；
- 认证令牌必须具有有效期（JWT，默认 480 分钟）；
- 关键 API 必须校验登录状态和角色；
- 对象级数据访问必须校验资源归属；
- 敏感配置通过环境变量管理；
- 真实密钥、数据库密码不得提交到 Git。

## 12. 数据与数据库需求

### 12.1 核心实体

users、roles、permissions、students、teachers、colleges、majors、classes、courses、course_prerequisites、curriculum_plans、curriculum_courses、teaching_tasks、teaching_classes、classrooms、schedules、course_selections、exams、exam_rooms、grades、evaluations、announcements、operation_logs

> 字段级设计见 [DATABASE.md](DATABASE.md)。

### 12.2 核心关系

```
学院 → 专业 → 培养方案 → 课程要求
     → 教师 → 教学任务 → 教学班
     → 学生 → 选课 → 成绩

课程 → 教学任务 → 教学班 → 排课 → 选课 → 成绩
课程 → 考试 → 考场安排
```

### 12.3 数据完整性

- 重要业务字段设置唯一约束；
- 核心关系使用外键；
- 选课记录防止同一学生重复选同一教学班；
- 关键状态变化必须记录操作日志（⚠️ 写入 V0.2 待实现）；
- 重要业务动作必须在事务中完成。

### 12.4 数据库迁移

所有表结构变更必须通过 Alembic migration 提交；禁止手工修改生产数据库结构代替迁移文件。

## 13. API 与前后端交互需求

### 13.1 API 规范

业务 API 统一使用 `/api/v1/` 前缀，响应结构保持一致，分页/排序/搜索参数统一命名。完整清单见 [API.md](API.md)。

| 业务 | 示例 API | V0.1 状态 |
|---|---|---|
| 认证 | `POST /api/v1/auth/login` | ✅ |
| 课程列表 | `GET /api/v1/courses` | ✅ |
| 课程详情 | `GET /api/v1/courses/{id}` | ✅ |
| 新增课程 | `POST /api/v1/courses` | ✅ |
| 学生选课 | `POST /api/v1/course-selections` | ✅ |
| 退课 | `DELETE /api/v1/course-selections/{id}` | ✅ |
| 我的课表 | `GET /api/v1/schedules/mine` | ✅ |

> 注：PRD 原文档中的 `/api/v1/grades/{id}/submit`、`/api/v1/grades/{id}/approve` 在 V0.1 中实际实现为 `POST /api/v1/grades/teaching-classes/{class_id}/submit` 与 `POST /api/v1/grades/approve`，以实际代码为准。

### 13.2 前后端职责

- 前端负责展示、交互和输入校验；
- 后端负责最终业务规则校验；
- 前端不得自行判断选课容量、成绩审核等关键业务结果；
- API 错误必须返回可识别的错误码和说明。

| 场景 | 预期行为 | V0.1 状态 |
|---|---|---|
| 课程已满 | 禁止选课，返回明确提示 | ✅ |
| 重复选课 | 禁止创建重复记录 | ✅ |
| 时间冲突 | 禁止选课或排课 | ✅ |
| 先修课程不满足 | 禁止选课 | ✅ |
| 选课未开放 | 禁止选课 | ✅ |
| 成绩已审核 | 普通教师不可直接修改 | ✅ |
| 无权限访问他人数据 | 返回权限错误，不泄露数据 | ✅ |
| 数据库事务失败 | 业务整体回滚 | ✅ |
| 导入数据格式错误 | 返回错误行和字段提示 | ⏳ V0.2 待实现 |
