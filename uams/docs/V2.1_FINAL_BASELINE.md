## 4. V2.1 重点问题

### 问题 A：用户管理前端缺失（TASK-001）
RBAC / 登录 / 权限隔离已通过验收；`/users` 后端存在（列表/查询/新增/重置密码/停用启用），但前端无 `userApi`、无路由、无页面。

### 问题 B：排名前端缺失（TASK-004 / TASK-007）
GPA 计算存在；班级/专业排名后端存在（`GET /grades/my` 实测返回 gpa=2.78 / class_rank=5 / major_rank=5）；但前端学生成绩页只显示「平均绩点」，不展示排名，也未调用 `/grades/my`。**计算能力 ≠ 用户可见功能。**

### 问题 C：必修课预安排前端缺失（TASK-009）
选修课选退正常（student/Selection.vue）；必修课预安排后端存在（`POST /teaching-classes/{id}/assign-required`），但前端无 `assignRequired` 调用、无按钮。

### 问题 D：批量导入前端缺失（TASK-010）
后端已确认真实存在：3 个导入（学生/课程/成绩）+ 3 个模板下载，实测模板下载返回真实 `.xlsx`（5004 字节）。但前端无 `importApi`、无导入按钮、无模板下载入口。**必须闭环到前端。**

### 问题 E：学期管理前端缺失（TASK-011）
数据统计正常（Statistics.vue）；学期管理后端存在（`/terms` CRUD + activate/end，实测 200），但前端无 `termApi`、无学期管理页。

### 问题 F：部署优化未完成（TASK-012）
实测确认：无 `start.sh`；后端未监听 `0.0.0.0`（uvicorn 默认 `127.0.0.1`）；`DEPLOYMENT.md` 明示「LAN 部署为规划内容，尚未配置」。

### 问题 G：排课前端联调不完整（TASK-013）

## 5. 重点业务问题：成绩权重冲突（→ FIX-008）

### 5.1 现状确认（本阶段已查证，未修改）

| 调查项 | 结论 | 证据 |
| --- | --- | --- |
| `Course.regular_weight/final_weight` 是否仍被生产逻辑引用 | **否（死字段）** | 全后端 `grep regular_weight/final_weight` 仅命中 `models/course.py` 与 `schemas/course.py`，无任何 Service/API 引用 |
| 演示数据如何生成 | `seed_demo.py` 现用 `ScoreService.compute(course, g)`（第 352 行） | 代码读取 |
| 历史成绩是否依赖旧规则 | **是（演示数据陈旧）** | grade id=28（PUB101, 32h, 平时87 期末56）库内 `total_score=68.40`，等于旧 `87×0.4+56×0.6` |
| 最终成绩计算唯一来源 | `ScoreService.compute` → `WEIGHT_RULES` | `score_service.py` 唯一计算入口；选课/录入/导入/种子均走此 |
| GPA 是否基于最终成绩 | **是** | `grade_point = score_to_point(total_score)`，GPA = 学分加权 |
| 排名是否基于 GPA | **是** | RankingService 基于 GPA 排序 |

### 5.2 冲突本质

1. `Course.regular_weight/final_weight`（默认 0.4/0.6，含 `CHECK regular_weight+final_weight=1.00`）是**未被使用的死字段**，且其默认值与 `ScoreService.WEIGHT_RULES`（32h→0.2/0.8）**不一致**，具有误导性。
2. 演示数据在旧权重下生成，`total_score` 与现行规则计算结果不一致（68.40 vs 62.20）。

### 5.3 FIX-008 成立理由（为什么 FIX-001～007 无法覆盖）

- FIX-001～007 全部是「后端已有、前端缺入口」的**前端闭环**任务；
- 本问题是「数据模型死字段 + 历史数据陈旧」的**数据一致性治理**问题，涉及可能的 DB 迁移与数据修复，性质不同；
- 它是 FIX-002 / FIX-003（排名/GPA 展示）的**正确性前置**：总评错了，GPA 与排名全错，因此必须先于排名验收解决。

> 详见 [docs/fixes/FIX-008.md](fixes/FIX-008.md)（本阶段仅规划）。

## 7. V2.1 完成定义

V2.1 的完成标准不是「所有后端 API 存在」，而是：

```
用户登录 → 角色权限正确 → 进入对应页面 → 看到真实数据 → 执行操作
   → 前端请求真实 API → 后端执行真实业务 → MySQL 数据真实变化 → 页面显示正确结果
```

即：**真实用户可操作的完整业务闭环**。每个 FIX 的验收都必须落到「数据库真实变化 + 页面刷新后结果仍正确」。
